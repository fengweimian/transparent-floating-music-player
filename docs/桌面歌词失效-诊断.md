# 桌面歌词「接收不到信息」诊断报告

> 诊断日期：2026-10-08 ｜ 基线版本 v3.8.0 ｜ **本次只诊断，未改动任何源码**
>
> ✅ **已修复并验收：v3.8.1（2026-10-08）** —— 「七、修复与验收」（共享层缺失 / 永远停在「暂无歌词」）
>
> ✅ **续修：v3.8.2（2026-10-08）** —— 「八、桌面歌词补齐行级兜底扫光」（酷狗等无逐字源的歌在桌面歌词没有扫光）

## 一句话结论

桌面歌词的**传输链路是通的**，但你看到的是「收到了数据 → 解析当场抛异常 → 被 `catch` 吞掉 → 清空」。根因是**桌面歌词页 `desktop-lyrics.html` 没有引入 `lyrics.js` 现在依赖的共享层脚本**，这个断裂从 **v3.6.0** 起就存在。

---

## 一、根因（致命，主因）

`renderer/desktop-lyrics.html` 的脚本引用只有两个：

```html
<script src="lyrics.js"></script>
<script src="desktop-lyrics.js"></script>
```

而 `renderer/lyrics.js` 在 **v3.6.0（提交 `4363c22`「三模板逻辑收敛」）** 被改成走共享层：

| 位置 | 代码 | 依赖的全局 |
|---|---|---|
| `lyrics.js:88` | `this.lines = XFLyrics.buildLines(raw, yrc, {...})` | `window.XFLyrics` |
| `lyrics.js:124-128` | `XFUtils.escapeHtml(...)` | `window.XFUtils` |

这两个全局由 `renderer/shared/lyrics-parse.js` 和 `renderer/shared/utils.js` 提供（都是自包含 IIFE，只往 `window` 挂对象）。**桌面歌词页没引这两个文件** → 在桌面歌词窗口里 `XFLyrics` / `XFUtils` 都是 `undefined`。

### 对照证据（同一次实测，同一台机）

| 页面 | 引入共享层 | `typeof XFLyrics` | `parser.parse()` |
|---|---|---|---|
| 主窗口 `index.html` | ✅ 有 | `"object"` | 正常 |
| 桌面歌词 `desktop-lyrics.html` | ❌ **无** | `"undefined"` | 抛 `XFLyrics is not defined` |

### 为什么表现是"收不到信息"

`renderer/desktop-lyrics.js:176-197` 的接收逻辑：

```js
if (data.type === "trackchange") {
  currentTrack = data.track;
  if (!currentTrack) { clearLyrics(); return; }
  try {
    const result = await window.electronAPI.music.lyric(currentTrack.id, currentTrack.server);
    if (result && result.lyric) {
      parser.parse(result.lyric, ...);   // ← 这里抛 XFLyrics is not defined
      parser.hasLyrics = parser.lines.length > 0;
      renderAt(0);
    } else { clearLyrics(); }
  } catch (e) {
    clearLyrics();                        // ← 异常被吞，歌词被清空
  }
}
```

异常被 `catch` 静默吞掉 → `clearLyrics()` → 窗口永远停在「暂无歌词」，且 `parser.hasLyrics=false` 让后续 `timeupdate` 也直接 return。**从用户视角看就是"完全接收不到"**。

## 二、次因（即使补上脚本仍会崩）

`renderer/desktop-lyrics.js:149` 调用了一个**不存在的方法**：

```js
currentEl.innerHTML = `<span class="dl-scan" ...>${line.chars
  .map((c) => parser.escape(c.text))     // ← Lyrics 类没有 escape 方法
  .join("")}</span>`;
```

`renderer/lyrics.js` 的 `Lyrics` 类方法清单（实测枚举）：

```
constructor, setMusicFolder, setShowTranslation, loadForTrack, parse,
findLineIndex, translationFor, renderAll, update, updateCharProgress,
findLine, clear
```

**没有 `escape`**。全仓库 `.escape(` 只有这一处引用（`lyrics.js` 自己用的是 `XFUtils.escapeHtml`）。后果：**带逐字歌词**（网易云 YRC / QQ QRC）的歌在这一行再抛一次 `TypeError: parser.escape is not a function`，逐字扫光整体失效。

### 第 3 处是怎么被发现的

第一轮验收里，合成逐字测试（`"[00:01.00]ni hao"` + YRC）与真实《演员》YRC 连续跑，结果 `currentText` 显示的是**上一轮的 `"nihao"`**，而不是新歌的 `" 作词 : 薛之谦"`。

根因：`currentCharLineIdx`（「已渲染逐字行」缓存）是**跨歌的模块级状态**，换歌时没有重置。新歌第一行 `idx=0` 若与旧值相等，`renderAt` 的 `if (currentCharLineIdx !== idx)` 判定「行没变」→ 跳过重建 `innerHTML` → 短暂显示上一首的逐字内容。

补上 `currentCharLineIdx = -1;` 后重跑，`currentText` 正确变为 `" 作词 : 薛之谦"` ✅。

## 八、v3.8.2：桌面歌词补齐「行级兜底扫光」（2026-10-08）

### 现象与根因

用户反馈：**酷狗音乐的《少年》在主界面有扫光，桌面歌词完全没有。**

先查「是不是桌面歌词没拿到逐字数据」，实测否掉了这个假设——

```
meting kugou → 少年(梦然) hash=5d93a1abc5ba5838d1128547a7fb4ef1
lyricLen=1827, lrcLines=84, stampedTokens=0   ← 纯 LRC，一个字级时间戳都没有
[by:天琴实验室AI生成v1.0]
```

**酷狗压根不提供逐字歌词**（meting 把它解密成普通 LRC 返回）。所以主界面看到的「扫光」不是逐字，而是 `lyrics.js:175-180` 的**②行级兜底**——按「本行开始 → 下一行开始」的时长匀速推进整行前沿，视觉上一样是条从左到右的光带。

而桌面歌词 `renderAt()` 当初只实现了①：

```js
if (line.chars && line.chars.length > 0) { /* 建 .dl-scan + 字级前沿 */ }
else { currentEl.textContent = line.text; }   // ← 无逐字 = 静态文本，零扫光
```

→ **不是缺数据，是桌面歌词缺了主界面那条兜底分支。**

### 改动（`renderer/desktop-lyrics.js`，单文件 3 处）

| # | 改动 |
|---|---|
| 1 | `updateScanProgress(scanEl, chars, time)` → 拆出 `scanPercent(line, nextLine, time)`，内部两条时间轴：①字级（原有）／②行级（新增，末行 +6s 兜底，与主界面同参） |
| 2 | `renderAt()`：把 `.dl-scan` 容器**提升为无条件渲染**——有 chars 拼字、无 chars 用整行文本，两条路共用同一个容器与同一份 CSS |
| 3 | `renderAt()` 的三处「清空当前句」分支 + `clearLyrics()` 补 `currentCharLineIdx = -1;` |

第 3 处是**改第 2 处时才发现的连带缺陷**：既然无逐字也开始建 `.dl-scan`，那么「元素被清空但 `currentCharLineIdx` 还是旧值」时，重建判定会跳过 → `querySelector('.dl-scan')` 拿到 `null` → 该行**永远**不再扫光。触发路径：seek 到首行之前（清空 DOM，idx=-1）再跳回同一行。

### 验收数据（CDP，真实 IPC + 真实酷狗歌词）

**A. 源确实没有逐字**（`music.search("少年 梦然","kugou")` → `music.lyric`）

```

parser.lines: 84        linesWithChars: 0     ← 84 行，0 行带逐字
```

**B. 行级兜底扫光生效**（第 17 行「都是一次收获」28.47→30.09s）

| 行内比例 | `--scan-p` |
|---|---|
| 0% | `0.00%` |
| 25% | `25.00%` |
| 50% | `50.00%` |
| 95% | `95.00%` |

**C. 边界回归**（seek 到首行之前再跳回）

```
before(渲染第0行): hasScanEl=true → renderAt(0.2)清空: hasScanEl=false → 跳回1.2s: hasScanEl=true ✅
```

**D. ①字级路径无回归**（真实网易云《演员》YRC，id `32507038`，57 行全带 chars）

取 15 字行「顺应时代的改变看那些拙劣的表演」（77.97→83.14s）扫 11 点，逐字前沿与「整行均分」对照：

两条曲线**不重合** → 证明字级分支仍在按真实字边界走，没被兜底逻辑吞掉。（末点 `t=83.14` 已跨到下一行，故显示下一行的 0%）

**E. 双行模式**：`#dl-next` 无 `.dl-scan`（下一句保持纯文本，与主界面一致）✅

**F. 异常汇总**：桌面歌词窗口 / 主窗口 的 console error 与未捕获异常**全为 0**。

### 遗留说明

- 主界面 classic 模板的兜底扫光**恒开、无开关**；template2/3/4 有 `settings.showScan` 开关。桌面歌词窗口是**独立 BrowserWindow**，不读 `showScan`，其扫光独立于模板设置（本次未改该行为）。
- 桌面歌词的已播/未播色沿用**桌面歌词自己的设置**（`desktopLyricsPlayedColor` / `UnplayedColor`，默认白/灰），**没有**跟主界面的红（`--char-color: #ff4d4f`）对齐。
