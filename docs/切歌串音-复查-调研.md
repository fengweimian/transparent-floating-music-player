# 「切歌后音频对不上」复查调研（v3.10.6）

> 调研时间：2026-11-07 · 版本 v3.10.6 · **仅调研，未改任何代码**
> 背景：v3.10.3 曾修过「切歌后声音还是上一首 / 点播放没反应」，本次复查是否还有同类残留。

## 一句话结论

**四套新版模板（t2/t3/t4/t5）没有复现串歌** —— v3.10.3 的 `stopAudioQuietly()` 方案有效，
7 类场景实测全部正确。**残留问题集中在经典模板（classic）**，它的修复方式不同
（只 `pause()` 不清 `src`），会留下「当前曲已换、音频源还是上一首」的潜伏状态。

---

测试方式：CDP 驱动真实窗口，hook `HTMLMediaElement.prototype` 的 `src`/`play`/`pause`

## 2. 经典模板的两处残留

### 2.1 取址失败后点播放 → 播上一首（已复现）

实测序列（《幻听》→ 点酷狗《起风了(旧版)》，后者取不到地址）：

```
播A:        src=幻听, paused=false, dur=273.2, ct=4.7
点失败歌后:  src=幻听(未变), paused=true          ← 音频仍是上一首
点播放后:    src=幻听(未变), paused=false, ct=11.7 ← 又播起上一首
事件日志: pause → setSrc(幻听) → play(幻听) → pause → play(幻听)
```

机理（`renderer/player.js`）：

```js
// 287 行：v3.10.3 给 classic 只加了 pause，**没有清 src**
_pauseBeforeFetch() {
  if (!this.audio.paused) { try { this.audio.pause(); } catch (e) {} }
}

// 301/326/352 行：三处取址前调用它
// 305/329/356 行：取址失败直接 return，src 仍是上一首
if (!result.url) { this._emit("error", {...}); return; }

// 309-310 行：但 currentIndex / currentTrack 在 await 之前就已经换成新歌了
this.currentIndex = index;
this.currentTrack = track;
const result = await XFApi.urlInfo(...);

// 390 行：playPause 只看 src 是否非空，不看它属于谁
playPause() {
  if (this.audio.paused) {
    if (this.audio.src) this.audio.play().catch(() => {});   // ← 播的就是残留的上一首
    ...
```

**当前为什么不算"永久串歌"**：`trackchange` 事件只在成功路径发出（`_emit` 在 305 之后），
而 `#track-name` 只由 `trackchange` 更新 —— 所以取址失败时**主界面标题也停在上一首**，
UI 与音频是自洽的，用户体验是「点了没反应 / 一会儿弹个错误」。

**但它是不折不扣的潜伏状态**：内部 `currentTrack` 已经是新歌、`audio.src` 是旧歌。
只要有任何一处 UI（队列高亮、桌面歌词、后续版本加的即时反馈）先按 `currentTrack` 渲染，
就会立刻暴露成「歌换了、音频还是上一首」。而且用户点的是搜索列表里的新歌，心理上已经认为换了。

### 2.2 取址期间点播放 → 先响一下上一首（已复现）

```
事件序列: pause(A) → play(A) → setSrc(B) → play(B)
```

取址要联网（付费歌 0.3~0.7s，走完整兜底链时更久），这段时间 `audio.src` 还是 A，
用户按播放就直接播 A；等 B 的地址回来再被覆盖。表现是「换歌瞬间响了一下旧歌」。

### 2.3 对照：新版模板为什么没这个问题

新模板走 `stopAudioQuietly()`，**同时清掉 src**：

```js
function stopAudioQuietly() {
  audio.pause();
  audio.removeAttribute("src");
  audio.load();
  ...
}
```

于是 `btnPlay` 里 `if (!song.url || !audio.src) playAt(currentIdx)` 会重新走完整取址，
不会去播残留源。**这是 v3.10.3 两套修法的关键差异。**

## 3. 另外三处隐患（静态确认，未实测复现）

### 3.1 `_errSong` 永不重置（t2/t3/t4/t5 同构）

```js
let _errSong = null;                       // 初始化时为 null
audio.addEventListener("error", () => {
  if (_errSong === song) return;           // 同一首只处理一次
  _errSong = song;
  failPlay(song, "音频地址已失效…");
});
```

`_errSong` 之后再无赋值。A 歌直链失效一次后被记为已处理，清理 url、重新取址、继续播放；
若 **A 歌第二次**直链失效（长时间挂着、或重新取址拿到的短链又过期），error 会被直接忽略
→ 音频静默卡住、UI 不提示、点播放也不重取（因为 `song.url` 还在）。

### 3.2 error 监听认错了歌（t2/t3/t4/t5 同构）

```js
audio.addEventListener("error", () => {
  const song = curSong();        // ← 用"当前 UI 的歌"，而不是"这个 src 属于谁"
  ...
  failPlay(song, ...);           // ← 可能把刚切过去的新歌停掉
});
```

切换 src 后旧资源的 error 若延迟派发，此时 `curSong()` 已是新歌 → 会 `failPlay(新歌)`，
表现为「刚切过去就报地址失效」。守卫只挡了 `!audio.getAttribute("src")`（切歌时已清源的情况），
挡不住「新 src 已就位、旧 error 才到」。建议加 `audio.src` 与 `song.url` 的归属比对。

### 3.3 移除当前播放曲后，队列非空却提示「请先搜索」

t5 实测：队列 3 首 → 播第 2 首 → 点移除 → `currentIdx=-1`，音频正确停止；
但此时队列还剩 2 首，点播放按钮会提示「请先搜索歌曲或选择音乐文件夹」。
不是串歌，是状态没接续（设计上也没打算自动播下一首）。

## 4. 两套模板行为差异（供决策，不一定算 bug）

| 场景 | 新版模板（t2~t5） | 经典模板（classic） |
|---|---|---|
| 取址失败 | 停音 + **常驻**原因提示，点播放重试 | 停音（但 src 残留）+ toast 一闪，UI 不切 |
| UI 切换时机 | **先切 UI**，再取址（靠 stopAudioQuietly 兜底） | 取址成功后才切 UI |
| 直链失效（error） | `failPlay`：停住 + 提示，不跳歌 | **自动 `next()` 跳下一首**（连续 3 次才停） |

最后一行值得注意：classic 的 `audio error → this.next()` 会让用户感觉「播着播着跳到下一首」。
如果连续几首直链都失效，会连跳 3 首 —— 这可能是「音频变成下一首」的另一种来源。

## 5. 建议修法（未实施）

| 优先级 | 问题 | 建议 |
|---|---|---|
| P1 | classic 取址失败/期间播旧歌 | ① `_pauseBeforeFetch()` 补 `removeAttribute("src") + load()`（与新版对齐）；或 ② `playPause()` 增加归属校验：`src` 不属于 `currentTrack` 时走 `_loadAndPlay(currentIndex)` 而不是直接 `play()` |
| P2 | `_errSong` 不重置 | 在 `playAt`/`startPlay` 成功时把 `_errSong = null` |
| P2 | error 认错歌 | 记录 error 时的 `audio.getAttribute("src")`，与 `song.url` 比对，不一致就忽略 |
| P3 | 移除当前曲后空状态 | `currentIdx = -1` 时把播放按钮行为改成「播队列首曲」或提示更准确 |
| P3 | 两套模板错误策略不一致 | 决定 classic 是否保留「自动跳歌」（保留也行，但要写进文档，避免被当成 bug） |

## 6. 复现方式

CDP 驱动 + 媒体事件 hook（脚本见 `.workbuddy/tmp/`）：

```js
// 只抓音频元素（⚠️ 必须过滤 HTMLAudioElement，
//   否则背景幻灯片 <video> 会覆盖引用，读到 12 秒的 mp4 时长 —— 本次调研踩过这个坑）
const d = Object.getOwnPropertyDescriptor(HTMLMediaElement.prototype, "src");
Object.defineProperty(HTMLMediaElement.prototype, "src", {
  get() { return d.get.call(this); },
  set(v) { if (this instanceof HTMLAudioElement) window.__songAudio = this; return d.set.call(this, v); },
});
```

- 连切：`__player.playAt(0..n)`（`__player` 由各模板暴露，`curSong`/`currentIdx` 是 getter）
- 队列点击：`#queue-list > *` 行内 `[data-idx]`（播放）/ `[data-rm]`（移除）
- 经典模板：没有 `__player`，走 UI（`#search-source` + `#search-input` 回车 → `.btn-play-now`）
